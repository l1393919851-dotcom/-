## 1. 值类型 vs 引用类型

**定调：** 区别在赋值语义（拷贝数据 vs 拷贝引用）和生命周期谁说了算，不在「栈还是堆」这句话本身。

| | 值类型 | 引用类型 |
|---|---|---|
| 典型 | `int`、`struct`、`enum` | `class`、`string`、数组、委托 |
| 赋值 | 拷贝一份数据 | 拷贝引用，指向同一对象 |
| 默认 | `0` / 全零 | `null` |

**深挖：**

- 值类型可以在堆上：作为 class 字段、数组元素（`int[]` 元素在堆上但是值语义）。
- 引用类型的引用本身可以在栈上。
- `string` 是引用类型但不可变，看起来像值。
- `struct` 实现接口会装箱；`readonly struct` 减少防御性拷贝。
- `ref struct`（`Span<T>`）不能上堆、不能进闭包，保证栈上安全。

**可主动引申：**

- **装箱/拆箱**：值类型当 `object` / 接口用。Dictionary 用 `enum` 当 key 若没传比较器，老版本会装箱。
- **`in` / `ref` / `out`**：大 struct 用 `in` 防拷贝；非 readonly 时 `in` 可能又拷一份。
- **Unity**：`Vector3` 是 struct；`transform.position.x = 1` 改的是副本。
- **DOTS**：`IComponentData` 必须是 blittable struct，不能有托管引用。

**追问：**

- 为什么 string 是引用类型？不可变 + 驻留共享，比每次拷贝整段字符划算。
- 为什么不把所有东西做成 struct？拷贝成本、不能继承、易过期副本。

## 2. 链表 vs 数组

**定调：** 复杂度表只是纸面；现代 CPU 上连续内存几乎总赢（缓存行约 64 字节）。

| | 数组 / List | 链表 |
|---|---|---|
| 内存 | 连续 | 节点散落 + 指针 |
| 随机访问 | O(1) | O(n) |
| 头尾插删 | 中间 O(n)（搬元素） | 已知节点时 O(1) |
| 缓存 | 友好 | 不友好 |

**要点：**

- `List<T>` 是动态数组，不是链表。
- 链表插入 O(1) 的前提是已经拿到那个节点；从头找仍是 O(n)。
- 游戏里几乎总是数组 / List。链表适合：头尾高频操作、LRU 节点串联、内核队列。

**可主动引申：** 空间/时间局部性；`ArrayPool`；跳表（Redis zset）；Unity `NativeList` / `UnsafeList`。`LinkedList<T>` 每个节点是 class，额外对象头 + GC 压力。

## 3. 链表有环怎么办

**定调：** 快慢指针判环；再跑一次找入口。

**做法：**

1. slow 走 1，fast 走 2，相遇则有环。
2. 找入口：一个指针回到头，两个都走 1，再次相遇即入口。
3. 找环长：相遇后再让 fast 走一圈。

**证明（加分）：** 头到入口 a，入口到相遇点 b，环长 c。slow = a+b，fast = a+b+kc，且 fast = 2·slow → a = c−b。所以从头和从相遇点同时走，会在入口遇。

**同组链表题可一起说：** 倒数第 k（先走 k）；中间节点（快慢指针）；反转（三指针）；删除（假头）；相交链表（走完自己接对方，和找环入口同源）。

工程上有环通常是 bug，用哈希或世代号排查，不是上线再 Floyd。

## 4. 内存对齐

**定调：** CPU 按对齐地址读写更快；编译器插 padding；影响结构体大小、缓存、SIMD、伪共享。

**要点：**

- 对齐值一般是字段大小与平台字长的较小者。`double` 常 8 对齐。
- `struct { byte b; int i; }` 常占 8 字节不是 5。
- `[StructLayout(Sequential/Explicit/Auto)]`，`Pack=1` 可紧凑但可能更慢。
- **缓存行伪共享**：两核改同一 64B 里两个变量，缓存行来回作废。多线程计数器要 pad 到 64 字节。
- **SIMD** 常要 16/32 字节对齐。
- 对象头：方法表 + sync block（64 位约 16B），空 class 也不为 0。
- GPU constant buffer、网络协议同样要对齐（HLSL cbuffer 16 字节规则）。
- DOTS：字段顺序影响 chunk 里能塞多少实体。

## 5. Dictionary 底层 & Hash 冲突

**定调：** 哈希表 = 数组 + 把 key 映射到下标；冲突不可避免，看怎么处理。

**.NET `Dictionary<TKey,TValue>`：**

1. `GetHashCode()` → 映射到桶
2. `entries[]`：hash / next / key / value；`buckets[]` 存链头下标
3. 冲突用 **数组内下标链**（链地址法），不是满地 new 节点
4. 相等用 `Equals` / `IEqualityComparer`
5. 负载因子约 0.72 扩容（素数容量），全部 rehash
6. 删除打 tombstone，避免断链

**冲突两派：**

- 链地址（.NET Dictionary）：实现简单，最坏 O(n)
- 开放寻址（Python dict）：省指针、缓存更好，删除难

**可主动引申：**

- 哈希碰撞攻击：恶意 key 全进一个桶。.NET 对 string 有随机化种子。
- 必须同时重写 `GetHashCode` 和 `Equals`；可变对象做 key 改字段后找不到。
- `IEqualityComparer<T>` 避免枚举装箱。
- `ConcurrentDictionary` 不能当普通 Dict 用；`HashSet` 是没有 value 的 Dict。
- Unity 热路径避免 string key；遍历无序。

**契约：** HashCode 相同不一定 Equals；Equals 则 HashCode 必须相同。

## 6. 对象池：为什么用 Queue，还有什么优化

**定调：** 池用空间换 Instantiate/GC；Queue 是语义清晰，并防止 `List.RemoveAt(0)` 变成 O(n)。

本项目：`GameObjectPool` 使用 `Dictionary<string, Queue<GameObject>>`。UI 池是「每种面板一份」的 Dictionary，不是 Queue。

| | Queue | List 当栈 | Stack |
|---|---|---|---|
| 取还 | 两端 O(1) | 只有删最后一个才是 O(1) | LIFO O(1) |
| 意图 | FIFO，公平复用 | 容易写成从 0 删 | 刚回收的立刻再用，缓存更热 |

**优化策略：**

1. 预热 / 分帧预热（一帧 Instantiate 太多也卡）
2. 容量上限 + 空闲收缩
3. 回收复位：粒子 Stop/Clear、刚体速度、Trail、Animator、音效
4. 缓存组件，禁止每次 `GetComponent`
5. 慎用 `SetActive` 风暴（会触发整条 OnEnable）；可改 layer / 移出屏幕
6. 按类型分池，key 用 prefab 实例 ID 优于字符串
7. 租约/handle，避免重复 Despawn
8. Debug 下记录谁 Spawn 没还
9. 与 Addressables 结合：池空时异步实例化
10. 切场景 `ClearAll`，避免 DontDestroy 泄漏

## 7. 多态

**定调：** 同一消息，不同对象不同行为；机制是运行时动态绑定。

- 编译时：方法重载
- 运行时：虚方法 / 接口 / 抽象类 → 虚表（vtable）
- 接口还有接口映射表，比单类虚调用更贵
- `new` 隐藏不是多态；`sealed` 方便 JIT 内联

**可主动引申：** 组合优于继承（策略/状态模式）；Visitor 双分派；Unity `MonoBehaviour` 虚生命周期；ECS 用 System 批处理替代热路径虚函数。

## 8. 内存泄漏

**定调：** 托管泄漏 = 该死的对象还被引用；非托管 = 忘了释放。Unity 两套都有。

**分类：**

1. 事件/委托没退订（静态事件、EventCenter）
2. 闭包捕获 `this`
3. 协程 / UniTask 没取消
4. 单例 / DontDestroy 抓住场景对象
5. 集合只加不减
6. Native：`NativeArray` 未 Dispose、未 Destroy 的 Texture
7. AB / Addressables 句柄没 Release
8. 运行时 `new Material()`、mesh 副本、粒子漏 Stop

**查：** Memory Profiler 看引用链；对比两次 Snapshot。事件用 OnDisable 必退订，或弱引用。

## 9. 反射

**定调：** 运行时读元数据；灵活且慢，IL2CPP 还会裁剪。

- `GetType` / `GetMethod` / `Invoke` / `Activator.CreateInstance`
- `Invoke` 参数数组装箱；第一次贵，之后可缓存成 Delegate
- AOT 要 `[Preserve]`，名字可能被 strip

**替代（显得跟得上）：** Source Generator；Expression 树编译委托；编辑器用反射没问题；xLua wrap 是提前生成调用，避开运行时反射。

热路径禁止反射。

## 10. 几种异步

**定调：** 异步 ≠ 多线程。很多异步只是先把主线程让出去。

| 方式 | 线程 | GC | 取消 | 适用 |
|---|---|---|---|---|
| 协程 | 主线程状态机 | IEnumerator / yield 可能有 | StopCoroutine | 简单流程、旧代码 |
| Task | 可能线程池 | 分配 Task | CancellationToken | IO、通用库 |
| UniTask | PlayerLoop | 结构体，几乎 0 | 同左 | 游戏首选 |
| Job/Burst | 工作线程 | 0（blittable） | JobHandle | 大量计算 |
| 回调 | 看实现 | 闭包 | 自己管 | 引擎底层 |

**注意：**

- 子线程不能碰 Unity API
- `WaitForSeconds` 受 timeScale；`WaitForSecondsRealtime` 不受
- Unity 的 `SynchronizationContext` 会把 await 切回主线程
- 死锁：主线程 `.Result` 等任务，任务又要回主线程
- Addressables、UniTask.Delay、DOTween 都是异步源

## 11. 闭包

**定调：** 函数带着定义时的环境；编译器生成隐藏类，捕获变量变字段，所以分配在堆上。

- 捕获值类型会把它提升成引用对象的字段，生命周期变长
- 每次 `() => ...` 往往每次 new 一个闭包对象
- 多播 `+=` 每次分配新 Delegate
- 老 C# `for` 循环捕获同一变量是经典坑

热路径缓存 `Action`；不捕获的静态 lambda 可能无分配。和事件泄漏绑在一起讲。

## 12. foreach 底层

**定调：** 语法糖；开销看被枚举的类型。

```text
enumerator = GetEnumerator();
try {
  while (enumerator.MoveNext()) { var x = enumerator.Current; ... }
} finally { enumerator.Dispose(); }  // 若实现 IDisposable
```

- 数组 / `Span`：变成 for，无分配
- `List<T>.Enumerator` 是 struct，直接 foreach 不装箱；类型写成 `IEnumerable<T>` 会装箱
- 遍历中增删会因 version 校验抛异常
- `yield return` 生成状态机 class，有 GC

DOTS / 热路径写 `for (int i = 0; i < list.Count; i++)`。

## 13. ECS / DOTS vs OOP

**定调：** OOP 围绕对象；ECS 围绕「同类数据的连续块 + 系统」。

| | OOP（GameObject） | ECS（Entities） |
|---|---|---|
| 数据 | 对象里东一块西一块 | 组件按类型紧挨在 chunk |
| 行为 | 虚方法、继承 | System 遍历匹配的组件 |
| CPU | 缓存差、虚调用 | 线性扫描 + Burst + Job |
| 适合 | UI、流程、少量复杂对象 | 海量同类（子弹、兵） |

**DOTS 拆开：**

- **Entities**：实体是 ID，组件是纯数据，System 是逻辑
- **Archetype / Chunk**：同一组组件放一起（约 16KB）。增删组件 = 搬家
- **Jobs**：多核依赖图
- **Burst**：LLVM 子集，无 GC、无托管
- **Baking**：子场景把 GameObject 烤成 Entity
- **SharedComponent** 不同会拆 chunk，合批变差

不是银弹：UI/流程别硬上。混合架构常见：玩法 OOP，战斗单位 ECS。可提 SoA vs AoS、数据导向设计（DOD）。

## 14. TCP 三次握手：两次有什么问题

**定调：** 三次是为了双向确认 ISN，并挡住延迟的旧 SYN。

1. SYN seq=x
2. SYN+ACK seq=y, ack=x+1
3. ACK ack=y+1

**两次的问题：**

- 旧 SYN 迟到会被当成新连接，服务端建立脏连接
- 服务端发出「我准备好了」后不知道客户端是否收到，半开连接占资源
- 第三次客户端 ACK 才真正建立（和半连接队列、SYN Flood 相关）

**可主动引申：**

- 四次挥手 + `TIME_WAIT`（2MSL）防止旧包进新连接
- 流量控制（滑动窗口）vs 拥塞控制（慢启动 / Cubic / BBR）
- 粘包：TCP 是流，要定长 / 分隔符 / 长度头
- 游戏玩法常用 UDP + 可靠层（KCP）；登录支付走 TCP/HTTP
- keepalive、心跳、断线重连

## 15. URP 渲染管线

**定调：** SRP 用 C# 描述一帧怎么画；URP 是面向移动/主机的实现。

**大致一帧：** Cull → Shadows → Opaque → Skybox → Transparent → Post Process → UI Overlay

（可选 Depth Prepass；2D Renderer 另一套。）

**可主动引申：**

- ScriptableRendererFeature / RenderPass 插自定义 Pass
- Render Graph：自动管 RT
- **SRP Batcher**：同 shader 变体少 bind，看 SetPass 往往比 Batches 更说明 CPU 痛点
- Forward+ / Deferred：灯光数量
- Volume、Camera Stacking
- vs Built-in：更可控；vs HDRP：更轻

半透明 Overdraw 是 GPU 问题，减 Draw Call 救不了。动静合批、GPU Instancing、GPU Resident Drawer 不要混成「都是合批」。

## 16. xLua vs 华佗（HybridCLR）

**定调：** 热更两条路——脚本虚拟机 vs 在 IL2CPP 上补解释/AOT 跑 C# DLL。

| | xLua | HybridCLR |
|---|---|---|
| 语言 | Lua | C#（热更 DLL） |
| 原理 | C# 注册 API，Lua 调 | 补充 IL2CPP 解释器，跑热更程序集 |
| 性能 | 跨语言调用有损耗 | 接近原 C#；热更部分略慢 |
| 工程 | wrap、两套 GC | 业务几乎不用改语言 |
| 适合 | 配表、UI、活动 | 新项目主逻辑热更 |

**还可提：** ILRuntime（更早，普遍不如 HybridCLR）；Lua + C# 混合；iOS 解释执行合规；热更分资源 AB / 代码 / 配表三层。AOT 泛型、裁剪、热点函数可挪回 AOT 程序集。

## 17. 事件派发：如何确定执行顺序

**定调：** 默认顺序不可作为协议；要顺序就显式优先级或流水线。

本项目 `EventCenter` 用 `Delegate.Combine`，顺序 = 订阅顺序，不能指定优先级。

**从弱到强：**

1. 约定 Awake/Start 订阅时机——脆弱
2. `(priority, id, callback)` 排序；同优先级再按注册时间
3. 分阶段：Pre / Normal / Post，或 Input → Logic → Presentation
4. 责任链 / 中间件
5. 关键路径直接函数调用，事件只通知刷新

**注意：** 派发中增删要先拷贝列表；异常隔离 vs 掩盖错误要说清；string 事件名可改枚举减 GC；`SendMessage` 反射且无序，别用。另有一套 Script Execution Order，不要和事件顺序混谈。

## 18. 单例 + 锁

**定调：** 单例解决全局唯一入口；锁解决第一次创建的竞争。Unity 主线程对象通常不必锁。

本项目纯 C# 单例是双重检查锁定；`MonoSingleton` 无锁，退出后返回 null 避免再创建。

```text
if (instance == null)
    lock {
        if (instance == null)
            instance = new T();
    }
```

**写法演进：** 静态初始化（线程安全）→ 双检锁 → `Lazy<T>`。

**锁可展开：** `lock` = Monitor，异常也要 finally 释放；读写锁、自旋、`Interlocked`；死锁来自锁顺序不一致；临界区尽量短。

**单例被骂：** 测试难、隐藏依赖、God Object。替代：DI、场景上下文。管理器单例常见，业务状态不要全塞一个类。

## 19. UI 优化：分 Canvas

**定调：** Canvas 是网格批处理单元；脏了就重建那一整块。拆 Canvas = 缩小脏区。

- 静态底 / 动态血条倒计时 / 飘字 HUD 分开
- 改文字、颜色、Rect 都可能脏
- 合批：同材质、同贴图、中间别插不同材质或 Mask
- 关掉无用 Raycast Target
- Overdraw：半透明层叠是移动端杀手
- TMP 动态字体加字可能卡顿
- 列表：虚拟化 + 对象池往往比分 Canvas 更重要
- LayoutGroup + ContentSizeFitter 嵌套会反复 Rebuild

**度：** 拆太碎 Batch 上升。实践大约三层，不要每个数字一个 Canvas。

## 20. 红点树

**定调：** 树 + 叶子计数 + 向上汇总 + 监听节点。

本项目：`RedDotManager.Register("Mail/Reward")`，`SetCount` 后父节点自动汇总，UI 只听 `"Mail"`。

**展开：**

- 叶子才设 selfCount，父节点只求和
- 一帧多次 SetCount 可脏标记，帧末再刷 UI
- 「未读数量」和「玩家点过没」分开存
- OnDisable 必须 RemoveListener
- 和成就/任务进度树同构

## 21. 进程 vs 线程

**定调：** 进程隔地址空间；线程共享内存所以要同步。

- 进程崩溃互不影响；线程切换更轻
- Unity 协程不是 OS 线程，是主线程状态机
- 主线程才能碰引擎 API；计算用 Job/线程池
- 可连到：上下文切换、锁、可见性/内存重排、临界区

## 22. 排序时间复杂度

**定调：** 比较排序下限 Ω(n log n)；线性排序需要额外假设。

| 算法 | 平均 | 最坏 | 稳定 | 空间 |
|---|---|---|---|---|
| 快排 | n log n | n² | 否 | log n |
| 归并 | n log n | n log n | 是 | n |
| 堆排 | n log n | n log n | 否 | 1 |
| 插入 | n² | n² | 是 | 1 |
| 计数/桶 | n+k | — | 是 | k |

**.NET `Array.Sort`：** 内省排序（快排 + 退化切堆排 + 小数组插排）。

**可提：** 三路快排（大量重复）；外部排序用归并；TopK 用堆 O(n log k)；LINQ `OrderBy` 会分配；每帧排序很贵，脏了再排。

## 23. 遮挡剔除

**定调：** 视锥之外不画；挡住的也不画。前者便宜，后者要数据结构或 GPU 查询。

- **视锥剔除**：必做
- **遮挡剔除**：Unity 烘焙 PVS；室内 Portal；GPU Occlusion Query / Hi-Z
- LOD、小物体屏幕占比剔除、距离剔除
- 透明物体一般难当遮挡物；动态角色对静态烘焙不友好
- 空旷野外收益小，烘焙还占包体

省的是提交和像素；若已是半透明 Overdraw 把 GPU 填满，先改材质和分辨率。

## 24. A* 寻路及优化

**定调：** `f = g + h`。h 可采纳则保证最优。

- Open：优先队列（堆 / 整数代价可用桶）
- Closed：已展开
- 不可采纳启发更快，但不保证最优

**优化：**

1. JPS / JPS+（规则网格）
2. 分层 HPA* / 路点 / 先高层再局部
3. 加权 ε-admissible
4. 双向 A*
5. 缓存、脏区域重寻、时间片分帧
6. 节点对象池

**Unity 更常用：** NavMesh A* + 漏斗算法拉直 + 局部避障（RVO）。海量单位 RTS 可提 Flow Field。大世界分块 Bake。

## 25. 操作系统临界区

**定调：** 访问共享资源、同一时刻只允许一个线程进入的那段代码。越短越好。

- 实现：关中断（内核）、自旋锁、互斥量、信号量；用户态 `lock` = Monitor
- 忙等适合临界区极短；否则睡眠
- 可重入 vs 不可重入；优先级反转与优先级继承
- 禁止持锁再调可能阻塞/加锁的外部代码
- 可连 CAS、ABA、内存屏障、无锁队列
- 游戏：能单线程就不共享

## 26. GC 回收

**定调：** 标记还活着的对象；停顿来自「找活对象」。C# 分代：Gen0 / Gen1 / Gen2 + LOH（≥85KB）。

- 根：栈、静态、寄存器、GCHandle
- 分代假说：大部分对象朝生夕死
- LOH 大对象，老版本不 compact，易碎片
- Unity Incremental GC 分帧标记
- 不要动不动 `GC.Collect()`

**减 GC：** 对象池、struct、不装箱、不 LINQ 热路径、少闭包、`StringBuilder`、缓存格式化字符串。托管堆 vs 原生堆（驱动、音频）在 Profiler 里往往 Native 更大。

## 27. 行为树

**定调：** 每帧从根 Tick，用 Success / Failure / Running 组合 AI。

本项目：`BehaviorTreeRunner` 按间隔 Tick；组合节点 Sequence / Selector / Parallel；装饰 Inverter / Repeat / UntilSuccess；叶子 Action / Condition / Wait；`BTContext` 当黑板。

**和状态机：** 状态少、转换明确用 FSM/HFSM；一堆条件+动作用行为树。还可对比 GOAP（目标规划）、Utility（分数选行为）。

**要点：** Running 必须记住下标（记忆型 Sequence），Wait/移动未完成不能每帧从头选；`Restart` 要 Reset。深层树可降 Tick 频率。

## 28. Lua 数据结构 & 模拟 OOP

**定调：** 几乎只有 table（数组部分 + 哈希部分）+ 元表。

```lua
Dog = {}
Dog.__index = Dog
function Dog:new(name)
    return setmetatable({name = name}, Dog)
end
function Dog:speak()
    print(self.name)
end
```

- `:` 会传 `self`；继承：`setmetatable(Child, {__index = Parent})`
- `pairs` vs `ipairs`；中间 nil 会断开数组部分
- 元方法：`__index __newindex __add __gc`
- userdata 接 C 对象；协程是 Lua 级协作
- Lua GC 与 C# GC 是两套
- 热更坑：旧闭包仍指向旧函数，方法应走表查找

## 29. AssetBundle

**定调：** 打包、依赖、加载、卸载、版本，五段都能说。

- 压缩：LZMA 包小解压慢；LZ4 可分段，运行时友好
- 加载：`LoadFromFile` 最快；用异步 `LoadAssetAsync`
- Shader / 共享图集单独打，否则重复或丢引用
- `Unload(false)` 只卸容器；`true` 连资产一起卸，还在用会粉红
- Addressables = AB + 编目 + 引用计数
- 和热更：AB 更资源，DLL/Lua 更逻辑
- 加密与性能权衡；场景 AB 还要 `LoadSceneAsync`

## 30. 粒子显示在 UI 前面

**定调：** Overlay UI 最后画，世界粒子插不进同一排序域。先统一 Camera + Sorting Layer，或把粒子画进 UI。

| 方案 | 说明 |
|---|---|
| Screen Space - Camera + 提高粒子 sortingOrder | 最常用 |
| 独立 UI 相机、层 mask、注意清深度 | 全屏特效 |
| UI Particle（粒子 mesh 进 Canvas） | 能合批，限制多 |
| 粒子渲染到 RT，RawImage 叠最上层 | Overlay 也能用，贵 |
| URP Renderer Feature 在 UI 前插 Pass | 管线级 |

粒子和 UI 都是透明队列，主要靠 sortingOrder 而不是 Z。Overlay 模式世界粒子永远在后面。Mask 要共享模板或 RectMask2D；Canvas 可 `overrideSorting`。
